# pr-review — 別セッションでのレビューとマージ可否の技術判定

## 0. 始める前に(必ず)

1. **モデルの確認**: このセッションが `claude-opus-5-5`(Opus 5.5。`.agent-kit/config.env` の
   `AGENT_REVIEW_MODEL`)で動いているか確かめる。違う・分からないときは、**別モデルでレビューせず**、
   「指定モデルで動いていない(現在: …)」と本人に報告して止まる。Claude Code では開始時に `/model claude-opus-5-5`。
   **セッションの最初から** Opus 5.5 で動かし、途中で変えない。サブエージェントに読ませない(セッション全体の応答のモデルで判定され、
   別のモデルが混ざると記録を拒否される)。
2. **別セッションであること**: この PR を実装した・確保したセッションではないこと。同じセッションならレビューしない。
3. リポジトリ固有の制限(例:「main へ変更しない・マージしない」)は常に優先する。

## 1. レビューする SHA を固定して読む

```bash
python3 .agent-kit/bin/agent-gh review-start <PR番号>      # 1行目にレビューする SHA が出る
git fetch origin <head のブランチ> <base のブランチ> && git checkout --detach <SHA>
```
- **固定した SHA の差分全体**を読む(前回のレビュー結果を流用しない)。途中で PR が更新されても、読んだのはこの SHA。
- 関連 Issue の「期待する動作」「受入条件/確認方法」「依存」を読む。

## 2. 確認する観点

| 観点 | 見ること |
|---|---|
| 仕様への適合 | 受入条件を1つずつ満たしているか。範囲外の変更が混ざっていないか |
| 不具合 | 境界値・エラー時・並行実行・既存機能への影響 |
| 設計 | 責務の分離、命名、依存の向き。不要な抽象化・過剰な複雑さが無いか |
| 保守性 | 巨大な関数、重複、読みにくい分岐、コメントの不足/過剰 |
| テスト | 受入条件に対応するテストがあるか。失敗系のテスト。実際に走らせた結果 |
| ドキュメント | 使い方・設定・移行が変わったなら更新されているか |
| 安全 | 秘密の混入、入力検証、権限、削除・課金を伴う処理 |

できる範囲でテストを実際に走らせる(`bash .agent-kit/bin/setup-deps.sh deps` の後に)。走らせられないものは「未検証」として列挙する。

## 3. 記録する

指摘は重大度を付けて書く(重大=マージ前に必須、通常、提案)。本文を一時ファイルに書いてから:

```bash
python3 .agent-kit/bin/agent-gh review-post <PR番号> --sha <固定した SHA> --verdict pass|changes|blocked \
  --blocking <未解決の重大な指摘の数> --body-file /tmp/review.md \
  [--unverified "マージ前に必要な未検証事項"]
```
- 重大な指摘が残る、または必要な未検証事項があるときは `pass` にしない。
- **終了コード 6**: レビュー中に PR が更新された。古い差分のレビューは投稿されていない。`review-start` からやり直す。
- **終了コード 4**: このセッションの応答に指定以外のモデルが混ざっている、または実装したセッション。本人に報告する。
- 記録には、モデルと独立性が「確認済み」か「未確認」かが入る(このセッションの transcript と hook の記録で確かめる。
  自己申告は使わない)。未確認のままでは merge-gate は合格にしない。本人が確かめたら、本人の端末で
  `agent-gh human-confirm <PR> --sha <SHA> --items model,session --key <鍵> --principal <名前>`(本人の鍵で署名)を実行してもらう(エージェントは実行しない)。

## 4. 判定を確認する

```bash
python3 .agent-kit/bin/agent-gh merge-gate <PR番号>
```
- 最新コミットのレビュー(モデル・独立性の確認を含む)・その SHA の**必須 CI**(ルールセット・ブランチ保護・
  `.agent-kit/ci-policy.json`)・依存・draft/WIP・コンフリクトを確認し、「マージ可(技術判定)」か「マージ不可」と理由を出す。
- 「マージ可」でも**マージ操作はしない**。本人(またはマージ権限を与えられた実行者)に結果を伝える。
- 実装担当が修正したら、新しい head でもう一度 1〜4 をやる。
